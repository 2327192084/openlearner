## 二、批注不渲染：根因不是页数，是公式选区

用户补充直觉：「不是公式的问题，前面几页划在公式上也正常，感觉和页数有关」。认真验了，结论是两者都对一半：

- 第36页恰好公式密集。这页共 5 条批注，纯文本的 2 条正常显示，含公式的 3 条不显示——正是用户截图「部分区域能正常显示」的现象。
- 根因：创建批注时存的是**屏幕上 KaTeX 渲染后的文本**（含零宽字符 U+200B、下标被拆成 `x \n 2 \n [n]`），而 prefix/suffix/start/end 取自**原始 LaTeX 源码**。两者不同源，重开时 `resolveTextAnchor` 找不到 → 判 lost → 跳过渲染。
- 试过「去零宽字符模糊匹配」救旧数据：匹配度只有 0.25/0.31/0.57（阈值 0.7），落点还错；硬放行会造成标记漂移。用户拍板：只治本，旧的手动删掉重标。

### 治本（两次才对）

- 第一次：公式选区把 `exact` 换成 `seg.text.slice(s,e)`。验证用的是 JS 构造跨片段选区，15/15 PASS——**假阳性**。
- 用户实测推翻：真实拖选整行公式时起终点都在同一 math 片段内部，`domPointToRaw` 对 math 片段起终点返回同一个 `rawFrom`，`s===e`，治本分支根本没进。
- 第二次：`mathSpanAt(node)` 找到所属 `[data-raw-math]` 片段的完整原文范围 `{from,to}`，起终点各自吸附，`s=startMath.from / e=endMath.to`，纯公式选区也 `s<e`。这次验证脚本改成「端点都在同一 math 片段内部」。
- 又一个坑：KaTeX 的 `.katex-html` 可见层整个带 `aria-hidden="true"`，脚本按 aria-hidden 过滤把用户实际拖选的文本节点全排除了 → `no visible text node in math`。改成直接取 `.katex-html` 下最长文本节点。
- 最终真实场景 17/17 PASS：新标记 exact 无零宽、`indexOf=29`、`start=29`，翻到35页再翻回36页仍正确还原，6 个 Highlight Range 全在正文里。

## 四、右侧工具栏固定：sticky 三次失败 → fixed

这是返工最多的一项，前三次「通过」全是假阳性（验证脚本滚错容器）：

- 用户滚的是**整个 document**（`.app` min-height:100vh 随正文长高），不是右栏内部。
- `position:sticky` 的包含块是 `.reader-split`（高度=整页正文），滚到底时 split 底边把 `.rside` 顶出视口（top 变 -48px）。
- 前两次验证脚本滚 `.rside__body`，第三次改滚 document 才发现真相。

最终改 `position:fixed`：右栏钉在视口右侧（`top:var(--topbar-h,51px)` 避开顶栏），正文让出 260px。窄屏（≤560px）退回 static 不遮挡。验证脚本改滚 `window.scrollTo(0, document.scrollingElement.scrollHeight)`，断言滚到底三个按钮仍在视口顶部。

## 九、教训

1. 验证脚本「滚错容器」造成的假阳性反复出现三次，直到用户实测才暴露。**必须按用户真实操作路径验证**（滚 document、拖选同一 math 片段内部）。
2. `domPointToRaw` 对 math 片段起终点返回同一 `rawFrom` 是治本第二次的关键；`dom-text-map.ts:232` 是 paint 侧依据，不能改。
3. KaTeX `.katex-html` 可见层带 `aria-hidden="true"`，构造选区不能按 aria-hidden 过滤。
4. sticky 依赖包含块，document 滚动场景下不生效；要钉视口就用 fixed + 正文留白。
5. 改 fixed 后记得所有兄弟元素（header/bar）都要留白，不只是正文区。
6. 打包后 `release/win-unpacked/openleaner-data`（52M 缓存垃圾）会被 NSIS 一起打进去让安装包从 98M 涨到 140M——打 NSIS 前必须先 `rm -rf` 掉。
