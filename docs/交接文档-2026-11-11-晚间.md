## 三、几个关键设计（供下一任理解，别推翻）

### 3.1 标注/备注的偏移：一套坐标系

**问题**：用户自己的标注一直画偏，而知识库定位的高亮是准的。

**真因**：两条路走不同坐标系。

- 知识库定位 → `MarkdownBodyMarked` 的 `marks` → 直接 `seg.text.slice()`，
  切的是原始字符串 → 永远准
- 用户标注 → `paintTextMarks` → 拿**原文偏移**去**渲染后 DOM 的文本节点**上累计

两者字符数不同。实测第 1 页：原文 1048 字，`.reader-md` 的 DOM 文本 **606 字**，
差 442 字。原因：标题 `## ` 被吃掉、`$v_{s}$` 经 KaTeX 变 `vs`、插图切成多段。

**修法**：渲染时把每片段的**原文坐标**写进 DOM（`data-raw` / `data-raw-len`），
换算按片段自带坐标做。见 `src/v2/ui/dom-text-map.ts`。

### 3.2 备注「先选后写」

用户原话：「备注功能先输入内容再选取我感觉有点怪，不符合使用日常习惯。」

流程：正文选中 → 选区浮层出现「写备注」→ 点它右栏自动切到备注页 + 光标落进输入框。

浮层渲染条件从「接了 AI」放宽为「任一动作可用」——
否则没接 AI 的用户拿不到这条路径。

### 3.3 解析的三种模式与合并语义

- **完整解析**：`--pages all`，整份重解析
- **分片解析**：`--pages 3-15`，只转这一段
- **合并写回**：`writeSegments(mode:'merge')` —— 新写的页覆盖同页，没写到的页保留

⚠️ **补位空页必须跳过**：分片解析 3-4 页时，`parseMarkdown` 会按
`page N of 36` 补出 **36 个页对象**，其中 34 个是空占位。
这些占位在 `merge` 时**绝对不能覆盖**已有正文 ——
否则就是用户报的「解析 3-4 页后，之前解析的前两页没了」。

标记方式：`MinerUPage.placeholder` → `ConvertedSegment.placeholder`
→ `WriteSegmentInput.placeholder`，`writeSegments` 的 merge 分支跳过。

### 3.4 MinerU 服务由程序自动启动

用户问过：「如果用户不懂如何启动 mineru 服务怎么办？能不能让 AI 帮忙？」

**结论：不用 AI，也不用用户敲命令。** 这个服务是程序自己的依赖 ——
exe 早就探测到了，`mineru server start` 只是一条子命令，主进程本来就能 spawn。

`ensureServerRunning()`（`electron/mineru.cjs`）：
先 `server status --json` 问一句（在跑就 1.9 秒返回）→ 没跑就 start
→ 轮询等它就绪 → 撞 `doclib.start.lock` 时按 1.5/3/4.5/6 秒退避重试 4 次。

### 3.5 重名资料消歧

用户库里有**两份同名 PDF**（同一次导入做了两次，内容不同），
列表里一模一样，已导致过一次误操作。

`src/core/source-title.ts` 的 `disambiguateTitles()`：
- **只给重名的那几份**加「（1）」「（2）」，不重名的保持干净
- 编号按 `createdAt` **升序**，所以编号**稳定** ——
  若按列表当前顺序编号，排序一变（「待解析」排前面）编号就跟着变，
  那比不加编号更糟
- 三个入口共用：资料页 / 文档解析页 / 整理知识点下拉

## 十二、给下一个模型的话

1. **「tsc 通过」不等于「功能在」** ——
   我把编号加到了 v1 文件，tsc 全绿，界面一动不动。
   **改完界面必须在真实应用里看一眼。**

2. **「我的脚本全过」不等于「用户看到的是对的」** ——
   上一轮我验了 `writeSegments(mode:'merge')` 的逻辑，说「合并做好了」，
   但真实链路上 `parseMarkdown` 会补出 34 个空占位，把正文清空了。
   **验证要覆盖真实链路，不是只测那一层函数。**

3. **用户报「两个入口看到不同内容」时，第一件事是去库里看数据。**
   我一开始猜渲染逻辑，绕了一圈；`diag-two-views.cjs` 一跑，
   `kind=docx, pageCount=2, segmentCount=36` 一眼看清全貌。

4. **不要连续猜三次。** 排查 `[Errno 13]` 时我先猜「瞬时锁」（加退避重试，
   4 次全失败），再猜「编码问题」（补 `PYTHONIOENCODING`，仍失败），
   第三次才去做**能证伪的实验**（直接测 Electron 进程的写权限）。
   两次猜测都不成立时，应该立刻换方法。

5. **不要把「改对了某个文件」当成「修好了」而感到满足。**
   本轮我改了 v1 的 css 并写了详细注释，一度以为解决了「过白」——
   实际那个文件 v2 页面根本没加载。**注释写得好不代表改对了地方。**

6. **这个项目里 v1 与 v2 并存。** 改任何东西前先 `grep App.tsx`。

7. **诚实报告边界。** 「自动启动服务」这条我在本会话环境验证不了，
   文档里如实写了「需要用户实测」，而不是含糊成「已验证」。
   宁可留下待确认项，也不要给一个假的绿。

### 写交接文档时的一条硬要求

**写交接文档时，同时在对话里直接输出一份「新对话启动提示词」**（不做成文件）。

⚠️ **格式要求（用户明确要求）**：

- **必须放在一个 ```` ```text ```` 代码块里，能一次全选复制。**
- **不要在代码块里用嵌套的 ``` 围栏** —— 那会把块提前截断。
  需要分段就用缩进或加粗标题，不要用三重反引号。
- 提示词要能**独立使用**：新会话不依赖本次对话的任何上下文也能开工。
- 内容至少包含：读哪几份文档（以及**不要读**哪份）、
  先跑什么命令验基线、几条硬约束、当前状态、最该先做什么、构建发布命令。

⚠️ **范围：只在用户要求「写交接文档」时做。** 不是每次回复都附。
