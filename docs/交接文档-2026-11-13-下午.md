他报的是「不符合实际」，实际是「名字在说另一件事」。**

### 2. ⚠️ 一段从来没生效过的旧代码，被新功能揭出来了

做「记住读到哪一页」时，我先去读 `ReaderPage` 里现成的滚动代码：

```ts

```

**这行代码从来没有生效过。** 实测：`.reader-body` 的
`scrollHeight === clientHeight`（932 = 932），它根本不滚。

而不是像注释里写的那样回到顶部。

这不是这一轮引入的 bug，是做新功能时顺手查出来的。见第四节。

## 四、⚠️ 那个「从来没生效过」是怎么被查出来的

### 起点

我要做「记住每段读到哪」，第一步是**读出现有的滚动位置**。
于是写了 `bodyRef.current.scrollTop`，拿到的永远是 0。

### 第一次猜（错的）

我以为「一开始就在顶部，所以是 0，正常」。于是先 `scrollTo` 到 200px
再读 —— 还是 0。这才意识到容器不受我控制。

### 决定性实验

写了一个探针，从 `.reader-body` 一路往上打印每个祖先的
`scrollHeight` / `clientHeight` / `overflowY`：

```
.reader-body    sh 931  ch 931  overflow auto   scrollable: false
.reader-main    sh 932  ch 932  overflow auto   scrollable: false
.reader-split   sh 932  ch 932  overflow visible
.reader-page    sh 1088 ch 1088 overflow visible
.page           sh 1152 ch 1152
.main           sh 1203 ch 1203
.app            sh 1203 ch 1203
DIV (无类名)     sh 1203 ch 818   ← 真正的滚动容器是它（= body）
BODY            sh 1203 ch 818
```

结论：**滚动发生在 document 上**。

### 为什么 `.reader-main` 也没滚

它写了 `overflow-y: auto`，但 flex 子项默认 `min-height: auto`
（= 不能比内容矮），所以它会随内容撑高，`scrollHeight === clientHeight`。

我补了 `min-height: 0` —— **但仍然不滚**。因为再往上一层的
`.app` 是 `min-height: 100vh`（会随内容长高），`.reader-page` 的
`height: 100%` 因此解析成「内容高度」而不是「视口高度」。

**要真让正文自己滚，得把 `.app` 改成 `height: 100vh` + `overflow: hidden`
—— 那会改变全站每一页的滚动行为，属于另一件事。**

### 这一轮的处理

**不动 `.app`。** 阅读器的滚动记忆改成用 document 的滚动位置
（`window.scrollY` / `window.scrollTo`）。理由：

- 改 `.app` 影响面是全站，风险与收益不成比例
- document 滚动本来就是现在实际的行为，按实际行为做记忆不会错

`reader-page.css` 里那段注释如实写明了这个取舍，
**包括「补了 min-height: 0 也不足以让它自己滚」** —— 免得下一个人
以为补一条 CSS 就能修好，又白查一遍。

### 教训

**「原代码这么写，一定是有用的」是错觉。**
那行 `scrollTo` 摆在那里、注释写得像那么回事，
但它在实际布局下从来没有执行成功过。

**判断依据只能是实测的数值**，不是代码看起来对不对。

## 五、关键设计（新增，供下一任理解）

### 5.1 阅读进度的字段分工

```
Source.readProgress = {
  furthestPage      读过的最远页码  → 「进度」百分比用它算
  lastPage          上次停留的页码  → 恢复位置用
  lastSegmentIndex  上次停留的段索引 → 恢复位置用（页码与段不是一回事，一章可能跨多段）
  lastScrollTop     该段内的滚动像素 → 恢复位置用
  lastReadAt        最后一次打开时间 → 「最近在读」排序用
}
```

**`furthestPage` 与 `lastPage` 必须分开**：往回翻之后当前位置变小，
但「读过的最远」不该跟着退。合成一个必然有一个是错的。

### 5.2 什么时候写、写多少

- 翻页 → 立即记一次（防抖 600ms）
- 滚动 → 记一次（同一个段内，不改变页码）
- 离开阅读器 → **补写**还没落盘的那一次（否则最后翻的那页会丢）
- 恢复位置的那一刻 → **不记**（`restoringScrollRef` 挡住，
  否则会把刚写进去的值又写一遍）

### 5.3 统计口径：一个屏上两个数字必须来自同一来源

统计页那个「今日明细」与首页这个「阅读进度」都遵循同一条：
**界面上的数字和列表必须对得上**。

阅读进度这块简单（进度条 = `furthestPage / pageCount`，文案同源），
但统计页那边踩过：「数字说 5、列表说 4」。
见 `src/v2/core/stats-today.ts` 里 `reviewedRows()` 的注释。

## 八、教训（写给下一个接手的人）

### 1. 「原代码这么写，一定是有用的」是错觉

这一轮那行 `scrollTo({ top: 0 })` 从来没生效过，而它摆在那里、
注释也写得像那么回事。**判断依据只能是实测数值。**

### 2. 反向验证要能区分「真的生效」和「什么都没发生」

阅读器滚动那一项，第一版断言是「翻走再翻回，位置和原来一样」。
这个断言**新旧两版都通过** —— 因为旧版翻页时既不滚也不记，
回来时位置恰好也没变。

加上「翻到下一段之后位置必须几乎归零」才区分得开
（旧版停在 18.8px，新版是 0）。

**教训：一条断言如果对「坏的实现」也成立，它就没在验任何东西。**

### 3. 「记忆系统」必须跨会话验

测试阅读位置时，如果只在一个 app 会话里「翻到第 9 段 → 回首页 → 再进」，
页面状态本来就还在内存里，看不出有没有真的落库。

正确做法：**读到第 9 段 → 把 app 彻底关掉 → 重新启动 → 再进**。
脚本里为此写了一个 `withApp()`，每次起一个独立进程、跑完就关、
并 `sleep 2500` 等 leveldb 落盘。

### 4. 校验数字要对着「同一份数据」比

这一轮又一次撞到：截图前没 `scrollIntoView`，
反馈块在视口上方 → **断言过了但图上根本看不见**。
还有一次截图截到了首页（页面已经跳走），三张图长一样。

**截图之前先确认「现在这一屏是不是我要拍的那个」。**

### 5. 断言全过≠没有 bug，排版只有肉眼能看

资料库「跳页」展开后把标题挤成竖排 —— 21 条断言全过，
因为断言查的是「有没有输入框」「能不能跳」。
**CSS 布局错乱不会让任何断言失败。**

所以改界面的项，必须真的看一眼截图。

### 6. 名字错了会连累数据的可信度

用户报「资料进度不符合实际情况」，实际是「名字在说另一件事」：
那块统计的是题目，不是阅读。

**一个标题名不副实，用户会对整块数据的可信度打折。**
改名之后必须真的补上那个东西，不能只改名。

### 7. 高频写入要单独一个方法，不要复用「改属性」的

`SourceService.update()` 会刷 `updatedAt`。阅读位置若复用它，
资料列表里的「最近修改」会全部失真 —— 用户只是翻了两页，
资料却看起来像刚被编辑过。

**「用户改属性」和「系统记状态」是两种写入，不该共用一个入口。**

### 8. flaky 名单（与上午那份一致）

- `src/core/parsers/pdf.test.ts` 的 `parseCourse`（依赖外部 fixture / 时序）
- `src/core/knowledge/service.test.ts` 的 `beforeEach`
  （并发负载下 `Hook timed out`）

两者单独重跑都全过。遇到先单独重跑，别急着归因到自己的改动。
