## 三、本轮发现并修复的缺陷

### 缺陷 1：PDF 在浏览器里根本解析不了（阻断级）

- **现象**：导入任何 PDF 都失败，报 `No "GlobalWorkerOptions.workerSrc" specified.`
- **危害**：P1 的主功能完全不可用。
- **为什么单测没发现**：`parsePdf` 允许注入 `pdfjs`，单测走的是注入路径，
  从来没跑过 `loadPdfjs()` 这条真实「动态加载 + worker 配置」的分支。
  是 `verify-p1.cjs` 在真实浏览器里跑出来的。
- **修复**：浏览器里设 `workerSrc`（用 `?url` 让打包器产出路径）。
- **修复后连带发现第二个坑**：`?url` 在 Node（单测）里会被解析成文件系统路径
  `E:\node_modules\pdfjs-dist\...`，导致 33 个测试全挂。
  最终按 `typeof window !== 'undefined'` 分支：浏览器设 workerSrc，Node 退回 fake worker。

> 这个缺陷值得单独记：它说明**单元测试通过 ≠ 功能可用**。
> 注入式设计让测试容易写，但也让真实加载路径成为盲区。

### 缺陷 2：DOCX 表格里的文字全丢

- **现象**：`word/document.xml` 里同时有 `w:p` 和 `w:tbl` 时，只取了段落，表格整个被跳过。
- **危害**：教材里表格常承载核心定义（对比表、公式表），漏掉等于内容缺失。
- **原因**：`collectParagraphs` 一看到 `w:p` 就 `return`，不再遍历同级其他键。
- **修复**：按 key 顺序遍历，遇 `w:p` 解析、其他继续下钻。

### 缺陷 3（队友发现）：验收断言假通过

- **现象**：PDF 解析全挂时，「扫描件能被识别」这一项仍然 PASS。
- **原因**：断言用正则匹配页面文字 `/读不出|扫描/`，而界面的固定说明里本来就有「扫描」二字。
- **修复**：改为读 IndexedDB 真实数据 —— 检查 `textStatus === 'no-text-layer'`
  且「段数 3 / 有文字的段 0」。**不看文案，只看数据。**

### 缺陷 4：验收断言写死分区数量

- **现象**：P1 新增 `sourceSegments` 分区后，P0 的「11 个分区」断言红灯。
- **危害**：加分区是正常演进，却让验收误报，会训练人「红灯了先看看是不是误报」——这很危险。
- **修复**：改为检查必需分区是否存在，不数总数。

## 五、如实说明的限制

- **真实拖拽未自动验证**：CDP 造不出带 `DataTransfer.files` 的 drop 事件。
  拖拽与点选共用同一 handler，但**真手拖需要人工点一次**。
- **扫描件的「看图模型」是 P6 范围**：P1 只做到「识别 + 给出建议」，不做 OCR。
- **DOCX 页数不是真实页码**：Word 文档没有固定页（取决于排版引擎与纸张），
  所以按章节切分，`page` 语义是章节序号。界面上应显示「章」而非「页」，
  这一点 P2 出题引用时需要留意。
- **PPTX 单页缺失不致命**：某张幻灯片 XML 缺失时会占位为空段而不是整份失败，
  避免一张坏页毁掉整份课件；但用户会看到一页空白。
- **`npm run build` 的 esbuild 临时目录问题**是 Windows 环境限制，非代码问题（README 已注明）。

## 六、给 P2 的交接

P2 要「从资料产出知识点」并做校对界面，有三件事已经就位、两件要注意：

**已就位**
1. `SourceLocation` 语义已精确固定（页内偏移，不是全文偏移）。
2. `SourceService.getSegments()` 返回按页有序的段，可直接作为 AI 的输入分片。
3. 导入失败已分类（六种 code + hint），AI 调用失败可以复用同一套展示方式。

**要注意**
1. **不要让模型自己编页码**。模型不知道真实页码，必须让它输出**原文引用文本**，
   再由我们拿文本在对应段里 `indexOf` 定位。定位不到就留空等人处理 —— 这正是
   计划书 P2 第 7 条的要求。
2. **校对界面必须能显示「定位失败」状态**。P2 验收要求「指认不到原文位置的条目单独标出来」，
   所以数据模型里 `KnowledgePoint.anchors` 允许为空数组，界面要有对应的空状态。
