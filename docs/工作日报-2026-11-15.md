## 二、DeepSeek 云 OCR（第 1 件）

### 先查官方文档，没照报道抄

`POST https://api.deepseek.com/v1/tools/ocr`
来源：https://api-docs.deepseek.com/zh-cn/guides/ocr

查出来的关键事实（都写进代码注释了）：

| 项 | 事实 |
|---|---|
| 请求 | `multipart/form-data`：`file`（带文件名）+ `purpose` |
| 响应 | `{ pages:[{index,text,finish_reason}], page_count, usage }` |
| 页码 | `index` **从 0 开始**，而全项目用 1 基 |
| 限制 | 100 MiB / 1000 页 / **180 秒总时长** |
| 计费 | 1.5 元 / 1000 页 |
| 限速 | 每账号 15 个并发，超出 429 |

**一个必须说的坑**：识别失败时 HTTP 状态码**仍然是 200**，响应体是
`{ error: {...} }`。只看状态码会把错误当成结果，然后用户看到
「解析成功但 0 页」。这条专门写了单测钉住。

### 关键落差：它不出插图

官方 OCR 只返回文字。而 MinerU 会切图、给位置、写回 `SegmentFigure`；
阅读器有「这一页有哪些插图」、图文页能点开原图。

所以这条路**不能替换** MinerU，只能并列。这个代价**写在选择器上**
（选之前就能看到），不是等解析完才发现图没了。

### 与项目里已有的 `src/core/ocr/` 不是一回事

那套（2026-11-06）是「PDF 页**渲染成图片** → 多模态模型看图」；
DeepSeek 是「**直接上传原文件** → 服务端解析」。
输入不同、计费不同、本地依赖不同。所以做成第三条解析路，不塞进那套里。

顺带发现：那套 `OcrService` 从写完起**没有任何界面调用它**
（`grep OcrService src/v2 src/pages` 零命中）。又一个「做了没接上」。
与本改动无关，但写进注释让下一个接手的人知道。

### 做法：伪装成 MinerURunner

`ConvertPanel` 只认 `runner.run()` 返回 `{ pageCount, pages[], tier, producer }`。
所以云 OCR 做成同形的 runner —— 界面侧一行都没改，只是「换一个 runner 实例」。
造第二个接口意味着进度/合并/补位/写回那套逻辑要复制一遍，复制必然漂移。

- `tier` 写 `'deepseek-ocr'`、`producer` 写明来源
- `figures` 恒为空数组、`chapter` 恒为 null（不编造）
- OCR 的版面标记（`<|ref|>…[[坐标]]`）默认剥掉：会污染正文与字数统计

### ⚠️ 分片上传没做（你选了，但这一版没实现）

按页切 PDF 要「每片重新拼成合法 PDF」，还要定「第二片怎么与第一片合并」——
那要动 `writeSegments` 的 merge 语义与页码范围校验。

所以这一版是**整份上传**，并在界面明写「超过 180 秒的大文件可能超时，
大书建议先分批」。没在注释里写「已按 10 页分片」——那会让下一个人
以为有合并逻辑，去查半天。

### 网络：两个坑

1. 直连 GitHub 不通（curl 返回 000）
2. 走 `http://127.0.0.1:7897` 代理通（200）
3. 但 git 用 **openssl** 后端报 `TLS connect error: unexpected eof`
4. 换 **schannel** 后端才通

交接文档里记的推送命令用的是 openssl —— 这台机器上现在要用 schannel。

### 安装包：不能用 electron-builder

项目 `build/installer.nsi` 的注释写明：electron-builder 的 nsis 目标是
**两步编译**（先编安装器、再释放卸载器、再嵌进去编第二次），
第 2 步在这台机器上稳定失败（`Install data: 0 / 8 bytes`）。

所以按交接文档的命令直接调 makensis：

```bash
cd build
"$LOCALAPPDATA/electron-builder/Cache/nsis-3.0.4.1/makensis.exe" \
  -V2 -INPUTCHARSET UTF8 \
  -DSOURCE_DIR="...\win-unpacked" -DVERSION=0.2.0 installer.nsi
```

产物：`OpenLeaner-0.2.0-setup.exe`，**101,750,750 字节**，
MD5 `557f09ceb1e04ff6277272e0682588b5`，已复制到桌面。

### 构建隔离

用 `git worktree` 在 `95268a8` 上单独构建，**没有切换主仓库的分支**
（含 OCR 的版本必须原地保留）。node_modules 用目录联接复用，

## 八、教训

### 1. 对含转义的代码，不要用 shell 脚本改

改 `stripOcrMarks` 的正则时，我用 shell 脚本改了**三轮**，
反斜杠被 heredoc + JS 两层吃掉，正则全废
（`/\[\[\s*-?\d+/` 变成 `/[[s*-?d+/`），文件还被改坏到 534 行（重复段落）。

最后用「write 工具 + `String.raw` + 逐行数组」才改对。
这正是硬约束 15 说的事 —— **我自己违反了两次，代价是四轮返工**。

### 2. 同一个改动不要在两个地方各提交一次

README 我在本地提交一次、又在临时 worktree 里提交一次，
造成历史分叉。正确做法是：**在 worktree 里改完、推完，再让主仓库
直接 `reset` 到那个提交**，或者干脆先想清楚哪边是唯一的真相来源。

### 3. rebase 参数要先用 `--dry-run` 或备份

`git rebase --onto A B` 的语义是「把 **B 之后**的提交接到 A 上」。
我写成 `--onto c90e08a 93e0811`，而 93e0811 之后没有提交 ——
等于把 OCR 提交排除在外，文件从工作区消失。

**幸好先建了备份分支。** 动历史的操作，先 `git branch backup-xxx`。

### 4. 项目自己的构建脚本 ≠ package.json 里的 target

`package.json` 写着 `target: nsis`，但实际要用 `build/installer.nsi` +
makensis。原因写在那个脚本的注释里（electron-builder 两步编译在这台机器上
失败）。**遇到构建失败先读项目自己的脚本注释，别只信配置。**

### 5. 推送用哪个 SSL 后端要实测

交接文档写 openssl，这台机器现在要 schannel。
`curl -x http://127.0.0.1:7897` 能通不代表 `git` 能通 —— 两者用的 TLS 栈不同。
