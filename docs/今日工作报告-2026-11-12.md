## 二、交付的功能

### 1. MinerU 一键安装（本轮最大件）

**用户原话**：「要是用户不知道怎么安装 python，不懂配置环境怎么办。有没有办法做个一键安装按钮？」

**核心结论**：不需要用户装 Python，也不需要我做特殊方案——**本机已有的 MinerU 本来就没用系统 Python**。
它带一个 `cpython-3.12.15-windows-x86_64-none`（python-build-standalone 产物）+ 独立 `uv.exe`。

所以流程是：下 uv → 由 uv 拉独立 Python → 建 venv → 装包 → 下模型。
全程不碰系统 Python、不写注册表、不要管理员权限。

**实测跑通**：uv ✅ / Python ✅ / venv ✅ / 包 ✅ / 模型 ✅，合计 **3.3 GB**。

**四条用户明确要求，全部落实**：

| 要求 | 实现 |
|---|---|
| 用户自己选盘，但只选一次 | 选完写进配置。venv 建好不能搬（pyvenv.cfg 与 exe 启动器都写死绝对路径） |
| 空间不够直接置灰 | 剩余 < 3GB 的盘标「空间不足」 |
| 要有卸载按钮 | 只删自己有标记的目录，不碰学习库，带二次确认 |
| （A 方案）已有的就别重装 | 探测到已有 MinerU 就复用。**理由不是省事**：它的 server 是全局单例，装第二份会 token 打架（实测 `invalid_doclib_token`） |

**安装包体积影响：0 MB**。体积全落在用户目录，只在点击安装后产生。

### 2. 题库单题编辑与删除

## 三、修掉的真实 bug

### 1. ⚠️ 分片解析会删掉没解析页的插图（用户实测发现）

用户报「解析那份 PDF（2）的 1-2 页时丢失了图片」。

**真因**：`importFigures()` 清理旧图时只按 `sourceId` 过滤，不看这次解析了哪几页。
于是每做一次分片解析，整本的图就被删一次。用户的图从 88 张掉到 6 张。

**这与上一轮正文那个 bug 是同一个形状**：正文那边早已改成按页合并，插图这条路还停在「整份重写」。

修法：`importFigures` 新增 `coveredPages`，只清本次覆盖的页。

**关键教训**：这个 e2e **第一版是假通过**。它在界面还显示「正在取回插图 1/5…」时就读库，
而实际顺序是「先取图 → 再删旧图 → 再写新」。用修复前的代码反向验证时才暴露——
它同样报 88→88。改成轮询到取图结束再读，反向验证立刻变成 88→5（83 张全灭）。

### 2. NSIS 卸载段会删掉用户数据

原卸载段注释写着「刻意不删 openleaner-data」，但上面一句 `RMDir /r "$INSTDIR"` 是**递归删整个目录**，
会把数据一起删掉——**注释与行为相悖**。用 `RMDir /r` 实测确认：整个目录全没了。

修法：删之前先把数据目录移到 `$INSTDIR` 之外，删完再移回来。

### 3. 发布脚本复用 Release 时不更新说明

原脚本只补传附件、不动 body。于是同版本号重新发布时，页面还挂着上一次的说明——
新加的一键安装已经打进包里，但「这一版做了什么」里没有它。

## 七、今天踩到的技术坑（供后续参考）

### 1. 下载会无声卡死

下 uv 时到 6.8MB 后 `reader.read()` **既不返回也不抛错**，界面永远停在那。
加了「45 秒无新字节就中止」判据（`STALL_TIMEOUT_MS`），实测生效。

**只看总耗时不行**——2GB 模型正常就要几十分钟。

### 2. 国内镜像选型（实测数据）

| 源 | 结果 |
|---|---|
| GitHub 直连下拉 uv | 22 KB/s，中途卡死 |
| ghfast.top | 连接失败 |
| gh-proxy.com | 2.5 KB/s（21MB 要两小时） |
| **阿里云 PyPI 拿 uv wheel** | 十几秒完成 ✅ |
| **南大镜像 python-build-standalone** | **7.12 秒** ✅ |

**关键细节**：`uv python install --mirror` 必须给**根**，不能带日期——
uv 会自己再拼一层 `<发布日>/`，带日期就变成 `20260623/20261013/...` → 404。

### 3. `Expand-Archive` 不认 `.whl`

报 `NotSupportedArchiveFileExtension`。先复制成 `.zip` 再解。

### 4. 缓存目录必须显式指定

- uv 默认写 `%LOCALAPPDATA%\uv\cache` → 受限环境报 `Could not acquire lock`
- ModelScope 默认写 `%USERPROFILE%\.cache\modelscope` → `[WinError 5] 拒绝访问`

两个都要改成跟安装目录走。

### 5. git 推送的两个 TLS 坑

`github.com` 解析到 `20.205.243.166`，直连不通；走代理 schannel 握手失败。
最终靠这个组合推上去：

```
git -c http.proxy=http://127.0.0.1:7897 -c http.sslBackend=openssl -c http.version=HTTP/1.1 push origin main
```

`HTTP/1.1` 解决了 `unexpected eof while reading`。

### 6. 验证脚本自己也会错（第二次了）

e2e 把编辑测成失败。原因：IndexedDB 的 `getAll()` 按**主键**顺序返回，
而界面按 `order` 字段排序——「改的是 A、查的是 B」。
加 `sort((a,b)=>a.order-b.order)` 即通过。

**这已经是今天第二次了**（第一次是图片那个假通过）。验证脚本出错时方向不确定：
既可能假通过，也可能假失败。

## 九、给下一个接手的人

1. **不要复制卸载器到别处执行。** NSIS 的 `$INSTDIR` 编译时写死，复制出去照样删原目标。
   这是我今天犯的最严重的错。

2. **破坏性验证必须有真隔离。** 要么复制整个安装目录，要么只做静态审查 + 单测。

3. **验证脚本要反向验证。** 用修复前的代码跑一遍，看它是否真的失败。
   今天两次教训都是这么发现的。

4. **不要用 `getAll()` 的顺序当界面顺序。** 库里的存储顺序与界面排序是两回事。

5. **失败要如实说。** 今天有 4 个测试第一次跑失败、重跑全绿（并发资源竞争），
   我选择写进提交信息而不是悄悄重跑算过。
