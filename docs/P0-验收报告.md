## 三、验收过程中发现并修复的 4 个真实缺陷

这四条是**跑出来的**，不是看代码看出来的。记录在这里是因为它们都属于
「界面看起来正常、验收报告也能写通过，但实际行为不对」的类型。

### 缺陷 1：加了后端，页面仍显示「后端 0」

- **现象**：保存后端后列表出现该项，但上方「库内记录 · 后端 0」不变。
- **危害**：界面说谎。用户会以为没保存成功，反复重试。
- **原因**：`BackendSection` 只刷新自己的列表，没有通知父组件重算统计。
- **修复**：加 `onChanged` 回调，保存/删除后重算计数。已补回归断言（验收项 21）。

### 缺陷 2：没有学习库时，「从备份恢复」入口不存在（严重）

- **现象**：未建库分支只渲染「创建学习库」，不渲染「从备份恢复」。
- **危害**：**换机器后的首个场景直接走不通**——用户拿着备份文件，却只能先建一个空库才能恢复。
  这正好打在「学习库能导出、能从文件恢复」这条验收的盲区上：原实现只在「已有库」时才给恢复入口，
  等于把最需要它的场景关掉了。
- **修复**：未建库分支也渲染恢复入口，并提示不需要先建空库。
  验收项 26 就是为这条补的：清库 → 重载 → 从空状态恢复。

### 缺陷 3：preload 接口与类型声明不一致

- **现象**：`electron/preload.cjs` 实际暴露 `{ platform, isElectron, versions: { app, electron, chrome } }`，
  而 `src/vite-env.d.ts` 声明的是 `{ platform, versions: { electron, chrome, node }, appVersion }`。
- **危害**：类型系统对着一个不存在的接口做检查，等于没检查。用到 `appVersion` 时会运行时 undefined。
- **修复**：以实际实现为准修正类型声明，并让 `detectEnv()` 校验 `isElectron === true`
  而不是仅判断对象存在。

### 缺陷 4：Electron 生产包一打开就是「页面不存在」（上线级，最严重）

- **现象**：`src/app/router.tsx` 用 `createBrowserRouter`（history 路由）。Electron 生产分支
  用 `loadFile dist/index.html` 加载，协议是 `file://`，此时 `location.pathname` 是
  `/E:/openleaner/dist/index.html`，匹配不到任何路由，落到通配 404。
- **实测复现**（不是理论推断）：
  ```
  打开 file:///E:/openleaner/dist/index.html
  pathname : /E:/openleaner/dist/index.html
  hash     : (空)
  正文     : 页面不存在 / 这个地址没有对应的页面
  ```
- **危害**：**浏览器里 29 项全过，打包后双击一打开就是错误页。**
  这是最危险的一类缺陷：所有验收都通过，唯独用户拿到的东西是坏的。
  原代码注释里写「Electron 深链接由主进程兜底」，但主进程并没有、也无法做这件事。
- **修复**：改用 `createHashRouter`。选它而不是「主进程加 app:// 自定义协议」的理由是：
  hash 路由**同时**解决两个部署目标的问题——`file://` 能跑（Electron），
  静态托管也不需要 SPA 回退配置（P7 的试用链接）。history 路由两处各要一份配置，多一个出错点。
- **防复发**：新增 `scripts/verify-desktop.cjs`（file:// 场景，9 项）与
  `scripts/verify-packaged.cjs`（打包产物，8 项）。**验收必须跑在产物真正运行的环境里。**

## 四、如实说明的限制

### Electron 窗口本身未能在本机实测（唯一未闭环项）

- `electron.exe --version` 裸跑退出码 3、无任何输出
- 加 `--no-sandbox` 能输出版本 `v38.8.6`，最小脚本模块可加载
- 连最小脚本、不建窗口、在 `app.whenReady()` 之前就 SIGSEGV；
  指定可写的 `--user-data-dir` 后能过 `whenReady()`，但卡在 Chromium 的 Mojo
  需要创建命名管道 `\\.\pipe\*` 被拒（`EACCES`）——用 Node `net.listen` 独立复现了同一限制
- **结论**：当前是非交互式桌面会话，无可用显示环境。属环境限制，非代码缺陷。

**已经做到的替代验证**（真实跑过，不是推断）：

|---|---|---|
| 打包能成功 | `electron-builder --dir` | 退出 0，`win-unpacked/OpenLeaner.exe` 210MB |
| asar 含正确文件 | `asar.listPackage` | main.cjs / preload.cjs / dist 资源齐全 |
| **打包产物真能跑** | 解包 asar，用 `file://` 加载 | 8 项全过（首屏、导航、建库、持久化） |

## 五、超出 P0 要求、但提前做掉的部分

计划书只要求「设置页骨架：先只做界面和数据保存，不联调」。实现时多做了三件成本很低、
但能避免后续返工的事：

1. **凭据与配置分表存储**（`secrets` 独立分区）
   不是「导出时记得过滤」，而是从存储层面就与可导出数据隔离。
   P5 验收要求「凭据不出现在导出文件、日志、界面截图中」，这条从结构上就成立了。

2. **可用状态由配置推导**，不是让用户手填「我可用」
   `direct-api` 缺 Key → 未配置；`agent-app` → 需登录。
   对应 P5 的「调用前就告知，不做点了才发现不能用」。

3. **两套存储实现跑同一组契约测试**（32 条）
   内存实现让 P2 的「用假后端跑通全链路、不联网不花钱」现在就具备条件。
