## 三、今天修的几个重要缺陷（按影响排序）

### 🔴 中文 PDF 读不出字，被误报成「扫描件」
你导入教材时看到的那句提示，当时确实是我的误诊。

**根因**：pdfjs 缺 cMap 配置。中文 PDF 多数用 CID 编码，没有 `ToUnicode` 表时必须靠 cMap 才能解码，否则返回空字符串，被我们判成扫描件。

**为什么测试没抓到**：我的测试样本是 Edge 打印生成的，恰好带 `ToUnicode`。

**修法**：把 169 个 cMap 随应用发布，解析时指定路径。**并且把「扫描件」和「解码失败」分成两种状态**——前者该换文件，后者是我们没解开，不该让用户白折腾。

### 🔴 Electron 双击没反应
exit 3、零日志。查了很久，最后确认是 Chromium 沙箱在 JS 执行前就崩了，只能靠启动参数绕过。已做启动器。

### 🟠 错题归集的结论会反
时间戳精度只到毫秒，连点两次作答时间戳相同，「最近一次」排不出先后，**答对了也移不出错题本**。改用单调递增序号。

### 🟠 单选题全军覆没
`extractTerm` 对结构雷同的表述返回同一个值，干扰项被全过滤，凑不出选项 → 单选多选一道都出不来，20 题只出 10 题。

### 🟠 你误判「总结能力差」
根源是界面没告诉你用的是示例后端。现在卡片上有「示例后端·非 AI」徽标。

## 四、关于你提的扫描件两条路

**两条都还没实现。** 界面上只如实标注了「计划中」和「P6」，没有放假按钮。

我实际诊断了你那份《信号与系统》：

```
含 /Image 对象 : 是      含 /Font 对象 : 否
每页算子       : 只有 paintImageXObject（只画图）
配不配 cMap    : 都是 0 字
628 页，44MB，纯图片扫描
```

所以软件判它是扫描件**是对的**。任何 PDF 解析库都读不出文字——文字在图片里。

### 我的实现建议（明天可执行）

**路线② 看图模型优先，但只做「按需转换」**
- 目标用户是备考学生，教材公式多，Tesseract 在公式上很差
- 628 页一次跑全书成本高，应该：选章节 → 给预估 → 用户确认 → 只转那几章

**路线① 本地 OCR 作为免费备选**
- 用 `tesseract.js`（WASM，浏览器内跑）
- 中文包约 20MB
- **必须标注准确率局限**，且 OCR 文本与被引用原文要分开存，否则错字会污染「点回原文」

### 顺带一个建议
那份 PDF 最省事的办法是**找一份带文字层的版本**。判断方法：在阅读器里试着用鼠标选中一句话，能选中就是有文字层。这比 OCR 628 页划算得多。
