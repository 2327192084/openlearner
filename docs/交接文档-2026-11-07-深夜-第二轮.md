## 一、本轮做了什么（一个提交 `ef6f42e`，共 90 次提交）

### 1. 学习库首页 —— 「和功能导览说的相差的有点大」

原首页给的是**新手三步引导**（「这些卡片从哪来」），而导览里写的是
「今天的安排、各门课的进度、最近在练的题」。两者不是一回事。

现在首页就是导览说的那三块：

| 区块 | 数据来源 |
| --- | --- |
| 今天的安排 | `todayOverview`：到期 / 可学 / 今天已做 / 正确率 + 掌握度条 |
| 资料进度 | `buildStudyMap`：按资料聚合掌握度、到期、错题，弱的排前 + 一句话「最该补的是…」 |
| 最近在练的题 | `reviewLogs` 最近 5 条（答错的标红） |

新手三步引导没删，挪到了 `!hasSources` 分支 —— 新用户仍然看得到。

> 为什么标题写「资料进度」而不是「各门课的进度」：`courses` 分区实测是**空的**，
> 界面上根本没有「课程」这个东西。真正的归属维度是资料与章节。
> 不写一个界面上不存在的词。

### 2. 学习流 → 学习地图

用户原话：「学习流的作用感觉也不是很有用，参考一下 studyhub 项目的功能」。

原学习流按**一份资料**排五步进度（导入→正文→知识点→出题→练过）。
问题：这五步走完一次就永远全绿，之后打开这一页没有任何新信息。

换成 StudyHub 的 study-map 思路：**跨所有资料**摊开掌握度，
按「资料 → 章节」可折叠树，每行给出练过几道 / 掌握度 / 到期 / 错题，
**最弱的排最前面**。每次打开都有东西可看。

来源（已写进 `MapPage.tsx` 与 `study-map.ts` 的注释）：
- `ui/study-map/map-model.js` —— `mergeProgress()` 按题数加权合并掌握度；
  `readExpanded/writeExpanded` 折叠状态存 localStorage
- `ui/study-map/DeckTree.jsx` —— 可折叠两级树
- `lib/mastery.js` —— 五档掌握度

**和 StudyHub 的差异**（照搬前想过）：它的树顶层是「课程文件夹」，
我们的 `courses` 是空的，拿空概念做顶层只会剩一层。所以顶层用「资料」。

### 3. 错题页 —— 折叠 + 两个归类维度

用户原话：「一旦错题多起来，界面会很繁杂，做个收起来的功能。
再增加错题类型分类的功能，不仅能根据题型分类，还能根据哪本书的哪一章知识点进行分类。」

- **分组 + 折叠**：默认全收起，一屏看全貌；点开才铺开题目
- **两个维度**：按章节/知识点（默认）/ 按题型，可切换
- 组内排序三选一：错得最多 / 错的比例 / 最近错的
- 每组只显示「N 道 · 最多错 M 次」+ 资料名

### 4. ⭐ 「让 AI 打标签」这个思路不必要（用户提的，我查完后否掉了）

用户的直觉是「要实现分类可能需要在出题阶段让 AI 对出的题打上标签」。

**查完数据后确认不需要**，分类信息全都已经在库里：

```
Question.knowledgePointId  →  KnowledgePoint.chapter   章节名
Question.anchors[]         →  .sourceId / .chapter / .page  出处
Question.kind                                          题型（本来就有）
```

所以「按哪本书的哪一章分类」是**纯聚合**：零模型调用、零存储迁移、零出题链路改动。

不采用 AI 打标签的三个理由（写进 `WrongBookPage.tsx` 注释了）：
1. 多花一次模型调用去生成一个**已有的字段**
2. 模型给的章名会和知识点里的章名**打架**（两处对不上，用户不知道信哪个）
3. 打标签只在出题时做 → **已有的 24 道题没有标签**，得重跑一遍才对得上

### 6. 第二轮反馈（同日稍后，用户看完截图又提两点）

**① 错题按知识点分仍然臃肿** —— 用户原话：「根因还是知识点太多太散的问题。
我们先改为按题组分类，按章节和知识点分类后续我再思考一下能不能做。」

- 默认维度改成**按题组**（题组是出题的自然单位，数量天然少）
- 章节/知识点、题型**都保留**为可切换项 —— 用户说「后续再思考」，不是否决
- 实测效果：用户库里 9 道错题从 **8 个章节组** 变成 **2 个题组**，一屏看完

**② 首页「最近在练的题」要改成「最近在练的题组（未完成）+ 错题」，且能跳转**

原实现列的是**单道题**（「求信号 x(at+β) 时…」），点不动，也没有下一步。

现在两块：
- **最近在练的题组**：练过 N/M、N 道错着 → 点进「我的题组」并**自动展开该组**
- **错题**：最近 5 道 → 点进「错题与待巩固」

> ### ⚠️「未完成」是推导，不是记录（重要）
>
> 做题进度**没有落库**。`ReviewPage` 的 `index` 只是 React state，一退出就没了
> （查过 `STORES`，没有 practice/session 这类分区）。
>
> 所以「未完成」只能从复习日志反推：
>
> ```
> 这个题组里练过（有过日志）的题数  <  这个题组在库里的题数
> ```
>
> 它不是「上次做到第几题」，而是「这组里还有几道从没碰过」。
> 界面写「练过 N/M」，**不写「进度 N%」** —— 措辞上不冒充真实进度。
>
> 没有为此新增数据表：那要动迁移三件套（DB_VERSION + schema + 迁移规则），
> 而收益只是「精确到第几题」。用现有数据就能回答「哪组没做完」，
> 不值得为它动数据库版本。见 `src/v2/ui/recent-decks.ts` 头部注释。

## 七、⚠️ 已知问题（接手后优先处理）

### 1. ✅ 判断题渲染 —— 已验完，并查出一个真 bug（2026-11-08 完成）

**做法**：在 `.tmp` 副本库里写一道判断题，把同题组其它题删掉让它成为唯一一张
（脚本里加了硬保护：路径命中 `release/win-unpacked` 直接拒绝）。

**渲染本身是对的**：题型标签「判断」、选项 T 对 / F 错、答错后正确项标绿
「正确答案」、所选项标红「你的选择」、给出解析、只给「下一题」。

**但查出一个真 bug**：判断题能同时选中「对」和「错」。
根因是 onClick 只判 `kind === 'single'`，判断题掉进多选 toggle 分支；
而 `canSubmit` 要求 `picked.length === 1`，于是选完两个后
**「提交答案」变灰、用户卡死在那一题、没有任何提示**。

修法：抽出 `src/v2/ui/option-pick.ts`（`isSingleChoice` / `pickOption`），
`ReviewPage` 改为调用它。为什么抽出来：项目只有 node 环境的纯函数测试、
没有 DOM 测试环境，内联在 onClick 里没法测 —— 而它正是出错的地方。
13 个单测盯着（`option-pick.test.ts`）。

> 教训：这条验证欠了三轮，因为一直「等模型出判断题」。
> 造数据比等概率事件可靠。

### 2. 真实模型不保证按勾选的题型出题（已大幅改善，但仍不能保证）

2026-11-08 加了「每种题型各出几道」（`kindCounts`）：
- 提示词从「尽量平均」改成逐种列具体数量（模型对数字的遵守率明显更高）
- mock 后端按配额严格执行（4 单选 + 2 问答就是 4+2，不再 3+3）
- 生成后界面仍如实报告「实际出了哪几种」

**真实模型仍是概率性的**，配额只是把「碰运气」变成「大概率照做」。
如果哪天发现模型经常不遵守，可以考虑生成后校验并在数量不符时提示重试。

### 3. `todayUtc()` 用 UTC 而不是本地日历

StudyHub 的 `lib/sm2.js` 明确偏离了上游库的 UTC 计数，理由是
「北京时间 07:50 和 08:10 跨了 UTC 日期，但用户觉得是同一天」。
我们 `src/v2/core/srs.ts:92` 正是 UTC 计数。**修它会影响所有 `dueAt` 语义**，
需要迁移测试 + 备份。

### 4. `answerRecords` 分区是空的

v2 从不写它（错题已改用 `reviewLogs`）。**不要在它上面做新功能**。

### 5. 「40 个分区」是加出来的数字

### 6. `smoke-release.cjs` 偶发连不上 CDP

实测：**单独跑稳定 5/5**。第一次失败是因为我同时开了

并发跑就会撞。**验证发布包时不要和别的 Electron 脚本同时跑。**

### 7. 做题进度没有落库（做「精确进度」前必须先决定）

## 九、给下一个模型的话

1. **不要动 `src/core/sources.ts` 里 PDF 原始字节的保存逻辑** ——
   pdfjs 会 detach `ArrayBuffer`，顺序不能倒回去。
2. **凭据、登录态、secrets 分区不进代码、日志、导出或提交。**
3. **不做假开关**：不做的功能就明说。本轮修的是**反向**问题 ——
   「开始复习」功能明明能用却标「还没做」，同样会让用户绕开真功能。
   两个方向都要查：**说了没做** 和 **做了说没做**。
4. **不指向不存在的地方**：说「去 X 页面做 Y」前先确认 X 真有 Y。
   `pages.ts` 的 `purpose` 就是「功能导览」上的原话 —— 改页面时同步改它。
5. **遇到需要拍板的岔路停下来问**。本轮用户拍板过：
   删「学新内容」按钮、删「20 张」和「5 分钟」两句、
   学习流改成学习地图、错题默认按章节分组、错题打标签走纯聚合不走 AI。
6. **保持轻量**：精确读文件片段和 grep，**不要整库扫描**。
7. **改 JSX 要小心**，尤其 `GeneratePage.tsx`（CRLF/LF 混用）。用 `scripts/_patch.py`。
8. **测试全绿不代表界面正确**。改完必须截图看一眼。本轮 9 个 bug 都是截图发现的。
   **尤其注意「同一屏里的数字要对得上」** —— 这是本轮最高频的错。
9. **⭐ 每轮开工前 / 遇到瓶颈时，先去检索（用户 2026-11-08 明确要求）**：

   > 原话：「在开始每轮对话的任务前或是项目遇到瓶颈时，先去网上检索（优先 GitHub）
   > 相关项目，看看有没有可复用的代码，或是可参考的处理方式，避免重复造轮子。」

   **两个触发点，不是只在「做新功能」时**：
   - **每轮任务开始前** —— 哪怕是修 bug，先查同类问题别人怎么处理的
   - **项目遇到瓶颈时** —— 卡住、返工、改不动的时候，先停下查，别硬推

   **查的顺序**：
   1. **先看 StudyHub 怎么做的**（同类产品，MIT，`lib/` 400+ 模块）：
      <https://github.com/EricWang1358/dsh-web-studyhub>
      raw.githubusercontent 在部分网络下不通，用
      `https://api.github.com/repos/EricWang1358/dsh-web-studyhub/contents/<path>`
      取 base64（`curl` + Python 解 base64）。**这条网络下实测可用。**
      已有的分析见 `docs/StudyHub源码分析-启发.md`。
   2. **优先搜 GitHub**：有没有现成库/组件/算法可以直接用或照着改。

      而不是自己写解析器。
   3. **再搜通用网络**：论文结论、官方文档、社区踩坑记录。

   **铁律**：
   - 查过的结论**写进注释并标明来源**（URL + 看了哪个文件）。
   - **搜到的代码要读、要验，不能盲抄** —— 尤其注意它依赖的运行环境
