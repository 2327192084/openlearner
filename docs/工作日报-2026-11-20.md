## 一、清理用户库 29 条悬空 `knowledgePointId`

**授权**：用户原话「先把坏数据请了」。

### 问题

`question.knowledgePointId` 本应指向 `knowledgePoints`，实测 **29 道题指向不存在的东西**：

| 类型 | 条数 | 来源 |
|---|---|---|
| `variant:q_xxx` | 19 | 变式题造出的伪 id（`questions/variants.ts:176`） |
| `seg_xxx` | 10 | 段落 id 被误写成知识点 id |

代码 2026-11-09 就修了（`service.ts:532` 只在 `origin === 'knowledge'` 时写），
**但旧数据没迁移** —— 而 `migrations.ts` 只处理**备份文件的版本升级**，
不是清理库内坏数据的机制。

### 为什么置 null 而不是回填

先做了回填探测，结论：**29 条一条都回填不了**。

- `variant:` 的原题已不在库里
- 锚点位置匹配也对不上：这些题的锚点是 `charStart:0 / charEnd:整段`，
  而知识点的锚点是真句子偏移（44~144 字），两者不可能相等

硬凑一个 id 就是编数据。项目一贯：**如实写 null，不给假 id**。

## 二、定位到句子：做了三轮才对

这是这一轮最反复的一件事，值得完整记录。

### 第一轮：只到页（问题暴露）

用户：「我看了复习库中所有题都标注了不能跳转到某一句子」。

根因：上一版把**题干**当 `quote` 传给阅读器 —— 题干通常不在原文里，
匹配不上，落地只到页首。

实测数据（用户库）：

| 数据 | anchors 实际内容 |
|---|---|
| 题目（23 道已发布） | `0 → 888/1366/1735`，**全部 = 整段长** |
| 知识点（104 条） | `44~144` 字，**真句子**，且带逐字 quotes |

### 第二轮：整段也标（用户提出的折中）

用户：「那我们退而求其次具体不到某一句子就让那一段落也高亮显示」。

加了 `.reader-mark--block`：比句子级淡一半（alpha 0.133 vs 0.28）、无描边、无圆角。
实测覆盖 **95%（588/618 字）**。

### 第三轮：撤销（用户看截图后推翻）

用户：「我看都是一整个页面被标注了，如果是整页标注的话那就不能称作段落，
那就不需要标注。」

**这个判断有数据支持**：实测 `avgSegmentsPerPage = 1.00` ——
他的资料**一页就是一段**，所以「标出这一段」等于「标出整页」。

于是回到 2026-11-09 那条更朴素的规则：**标不出来就不标**，
只显示页码 + 一句说明「精确不到具体句子，所以不标注」。

### 最终答案：从知识点出题能精确到句子

| 来源 | 锚点跨度 | 能否到句子 |
|---|---|---|
| 从原文出题 / 自选改造 | 888~1735 字 = 整段 | ❌ |
| **从知识点出题** | **44~144 字 = 真句子** + 逐字 quotes | ✅ |

`pointsToMaterials()` 把知识点 anchors 原样继承给题目并补上 `quote`，
阅读器就能用「偏移 + 引文校验」双重定位。

**而且用户自己已经验证过了**：他当天新建的 `deck_0f24e` 里那 2 道题
带真实 `knowledgePointId`、锚点跨度 47/57 字（段长 1675/1767，占比 3%）。

## 三、跨资料全文搜索（从零做起，三次迭代）

交接文档列为「建议的下一项」，理由写得很准：只能在某一本书里搜，
而真实场景是「我记得在哪本书看过这个概念」。

### 迭代 1：基础版（顶栏搜索框）

- 新增 `getAllSegments()` **一次读全表** —— 循环 `getSegments(sourceId)`
  是 O(资料数 × 全表)（它内部每次 `getAll` 再过滤）
- 纯函数 `src/v2/core/global-search.ts`
- **顺带修掉一个真 bug**：`ReaderTarget` 根本没有 `segmentId` 字段，
  导致阅读器只能按 page 猜段（而 page 在一份资料里不唯一）。
  实测现象：点搜索结果进了阅读器、页码对了，**但正文没有任何高亮**。

### 迭代 2：打磨（实测发现的三个问题）

| 问题 | 实测证据 | 修法 |
|---|---|---|
| **静默截断**（说的是假话） | 搜「的」实有 **2365 处**，界面显示「共 500 处」 | 拆 `matchCount`（真实总数）/ `total`（展示条数） |
| 第一本书吃光额度 | 高数 515 处占满 500 条，另两本（566/1284 处）一条不列 | 按 `floor(limit / 有命中的资料数)` 保底配额 → 167/167/166 |
| 500 条平铺滚不动 | 面板限高 620px | >80 命中时每组默认列 3 条 + 「展开全部」 |

### 迭代 3：独立成页（用户要求改 UI）

用户：「新开一个功能栏在课程准备与管理那里，然后界面参考 Google 或是 bing」。

借搜索引擎三样：居中大搜索框（620px，是顶栏的 1.9 倍）、
**命中概览分布条**（窄面板做不到的事）、结果三段式。
不借：输入即搜（会卡）、相关性排序（本地没词频模型，硬造不可解释）。

### 迭代 4：搜索历史（用户给参考图）

一排胶囊标签 + 「清空」，存 localStorage（不是学习数据，不进备份）。

## 五、这一轮踩的坑（都是新的）

1. **断言与界面的时差** —— 这轮最贵的一条：
   - 点搜索结果后只等 `.reader-page` 出现就查 mark → 查到 0（高亮是第二步 effect 画的）
   - 搜第二个词后只等「有摘要元素」→ 上一次的摘要还在 DOM 里，假通过
   两次都表现为**功能看起来坏了，其实是测试太急**。
   断言不能比界面快一步，也不能比它慢一步。

2. **`.page` 是 flex 容器，子页面会按内容收缩**
   搜索框实测只有 279px（比顶栏那个 329px 还窄）。
   别的页面没暴露是因为内容够宽（表格、卡片把宽度顶开）；
   搜索页内容轻，收缩最明显。修法：`.spage` / hero / bar 都显式 `width: 100%`。

3. **`46ch` 在中文里 ≈ 23 个汉字**
   说明文字被挤成两行窄条。改 `560px` 一行读完。

4. **模板字符串里的注释不能带反引号** —— 会提前结束字符串（语法错）。

5. **正则里的双反斜杠**：`/\\d+/` 在 JS 字面量里匹配「字面反斜杠 + d」，
   永远命中不了数字。用 `[0-9]+` 更稳。
