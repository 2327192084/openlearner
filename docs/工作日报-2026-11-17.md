## 四、PPT 看原件（本次最大的功能）

用户要「导入 PPT 时像 PDF 那样看原件；文本仍用于总结、出题」。

### 方案选择的曲折
- 最初的思路是用 LibreOffice 引擎把 PPT 转 PDF，但引擎包 182 MB（单个 exe 170 MB），打包后安装包约 151 MB，**压不进用户要求的 100 MB**。

- `src/core/sources.ts`：PPTX 也存原件字节（`storeOriginalFile` 的 PDF 专属闸门放宽），文本提取链路不动。
- `src/v2/ui/ReaderPage.tsx`：原图渲染 effect 与 `canShowOriginal` effect 放宽到 `pdf || pptx`，按 kind 选渲染器。

## 六、阅读器全屏沉浸查看

用户拍板：真全屏 + 收起右栏/搜索框，文字与原文都能用。

- `ReaderPage.tsx` 加 `isFullscreen` state、`fullscreenchange` 同步、`toggleFullscreen`、Esc 兜底；header 加全屏按钮（`data-action="fullscreen"`）。
- `reader-page.css` 用 `.app:has(.reader-page--fullscreen) > .sidebar / .topbar` 隐藏外壳（据 `AppShell.tsx` 实际结构，不是猜类名）。

**关键 bug**：首版把 `setIsFullscreen` 放在 `await requestFullscreen()` 之后，CDP 非 trusted 点击下 promise 不 settle → 点了没反应（10/17 FAIL）。改为「先立即翻转 state，再异步 request/exit，失败保留纯沉浸」→ 17/17 PASS。教训：全屏 state 不能挂在 Fullscreen API promise 上。

最终验证：隔离 CDP 22/22 PASS，桌面安装版 13/13 PASS；截图肉眼复核中文幻灯片铺满、外壳全收起。`electron:pack` 后同批替换 exe+asar，真实库 diff 空。

## 十、教训

1. **验证要先确认验的是对的东西**：用「信号与系统」当匹配词，命中的是旧 PDF，9/9 假阳性。独特 marker + 「目标确为刚导入的 PPT」断言才可靠。
2. **界面文案也是功能**：功能收敛后，残留的「用分片解析再跑一次」「大书建议先分批」就是说谎，肉眼截图才发现。
3. **全屏 state 别挂在异步 API 的 promise 上**：非 trusted 点击下 promise 可能永不 settle，先翻转 state 再异步请求。
4. **复制 Electron 运行时必须连 `resources/` 一起**，且 `openleaner-data` 这类缓存垃圾绝不能进安装包。
5. **打包/推送都要实测具体路径**：github.com 直连不通、undici 大文件上传不稳、makensis 才是正确的安装包构建方式——每一步都用事实校准，不照文档照抄。
