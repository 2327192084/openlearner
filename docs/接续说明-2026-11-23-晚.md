## 2. 最重要的结论：Obsidian 插件解析器的九条实测

**不要凭文档或博客写导出逻辑** —— 我这么干过一次，差点写错。正确做法是跑插件的真代码。

取证方式：下载已发布的 `main.js`（sha256 `e2af1a34…`，与 Release digest 逐字节一致），
按 `// src/xxx.ts` 分节注释切片拼成 harness，真跑 `parse()` / `CardFrontBackUtil.expand()`。
产物在 `.tmp/sr-verify/`（`FINDINGS.md` 453 行 + harness + 40+ 用例）。

| # | 结论 | 对实现的约束 |
|---|---|---|
| 1 | 纯 callout 里没有 `==…==`/分隔符 → **0 张卡** | callout 版式**必须**配合填空，否则一张都进不了队列 |
| 2 | callout 里写 `> ?` 也是 0 张（整行 trim **全等**比较） | 分隔符不能靠前缀，`"> ?"` ≠ `"?"` |
| 3 | 行含 `==…==` → 1 张 Cloze 卡，整段 callout 合成一张 | `> ` 前缀无害 |
| 4 | 一个 callout 里 N 个 `==…==` → **N 张独立卡** | 只包一处答案；正面已有挖空就别再包 |
| 5 | 裸 `??` → 自动生成反向卡 | 双向开关用它，只在 review 版式 |
| 6 | 标签行会被**吸进卡片正面** | 标签行与卡之间必须真空行 |
| 7 | 卡之间用 `>` 分隔 → 并成一张、答案互相泄露 | 卡间只能真空行 |
| 8 | 行内 `::` 是**子串**匹配 | 正文含 `::` 要打断（导出插零宽空格） |
| 9 | Anki `{{c1:…}}` 不支持，且被 `::` 静默劈坏 | 不生成该语法 |

> 任务描述里提到的 `src/parser/`、`src/regular-expressions.ts`、`SINGLE_LINE_CARD`
> 在 1.15.4 与 1.9.0 **都不存在**，是多年前的旧结构（博客仍在抄）。真解析器是 `src/parser.ts`。

`community-plugins.json` = `[]`）。所以导出的文件现在只是普通笔记，装上插件才生效 ——

## 3. 两个实测抓出来的真 bug（都差点交付）

### 3.1 导出卡粘连：导出 5 张、插件只认 1 个 question

原因：我用 `section.join('\n')` 单换行拼卡，而插件是"空行结束一张卡"。
把真实导出产物喂进 `parse()` 才暴露。修法：`cardBodies.join('\n\n')`。

**这个 bug 单测抓不到** —— 原来只有 `expect(content).toContain('#flashcards')`，它只查标签在不在。
所以补了结构断言"数有几段 callout = 卡数"，并做了反向验证确认它真的会红。

### 3.2 一张卡裂成两张

原因：那张卡正面本身含 `==::==`（用户手写的挖空卡），我又把答案包了一层 → 两个 `==…==` → 展开成 2 张。
修法：`const frontHasCloze = /==(?:[^=\n]|=(?!=)){1,200}==/.test(front.text)`，有就跳过包答案，
并返回 `cloze: 'front'` 说明"靠用户自己的挖空进队列"。

### ① 这个 bug 的真正根因（值得记住）

标签 chip 是**从当前数据算出来的**（`collectTags(cards)`）：
删掉某张卡上唯一的那个标签后，chip 消失 —— 但 `filter.tag` 还留着旧值。
`filterCards` 拿这个已经不存在的标签去筛，结果 0 张；而用户**看不到那个 chip，也就没有入口取消它**。
**这不是"筛得严"，是死锁。** 修法刻意**不是**在 `filterCards` 里悄悄忽略不存在的标签 ——
那会让用户以为筛着某标签、实际看到全部，属于更坏的谎言。

### ③ 为什么文件夹归属存 settings 而不是给 Flashcard 加字段

照 `src/core/resource-service.ts` 头注释的三条理由（本项目既有先例 `sourceResources`/`sourceTrees`/`studyPlan`）：

1. **一次写入天然原子** —— 加字段要遍历全库改每张卡，中途失败会留半截状态；
2. **不动迁移四件套**（`STORES` / `BACKUP_STORES` / `StoreRecordMap` / `DB_VERSION`），零迁移；
3. **`sanitizeSettingsForExport` 是整体展开的**（只 delete 凭据），新 settings 字段自动进备份，没有白名单要维护。

另外还有一条本项目特有的：备份导入两表（`flashcards` 与 `settings`）顺序不确定，
归属存 settings 就不会出现"卡片已导入、归属指向还不存在的文件夹"的中间态。

文件夹语义按用户选的**一个（像目录）**：一张卡只属于一个文件夹（`assigns: Record<cardId, folderId>`），
而不是多个标签式分组。`groupByFolder` 按**用户建的先后顺序**排（不按卡数 ——
按卡数排会让"刚建的那个"跑到第 5 个，用户会以为没建上）；
**空文件夹照样显示且计数 0**（否则点完"新建"界面没反应）。

### ④ 为什么批量删进回收站、单卡删不进

`src/core/flashcards.ts` 原头注释写明"闪卡往往是临时记一下就删的便签式内容，不写 reviewRecords，
删卡不进回收站，代价是误删不可恢复 —— 所以界面删除必须二次确认"。

**这次刻意做成不对称**：单卡删维护原行为，批量删（整组 / 整个文件夹）进回收站。
理由：单卡误删最多丢一张；一次点错删掉一整组 11 张，用户没法重打一遍。
这条理由已写进 `flashcards.ts` 头注释的新增小节，不是只在文档里。

需要动的地方（漏一处就是"进得去出不来"）：
- `src/core/model.ts` `TrashKind` 加 `'flashcards'`
- `src/core/trash.ts` `putBack` switch 加 case（**那个 switch 没有 default，加新 kind 不补 case 会静默什么都不做**）
- `src/v2/ui/TrashPage.tsx` `KIND_LABEL` 加「闪卡」

- 组头数字之和 = 列表卡片数（10 = 10）
- 点组头勾整组：已选数 = 该组卡数（**且必须 > 0**，见 8.3）
- 多选态下导出按钮张数 = 已选张数（**且 > 0**）
- 归入后该文件夹组头计数 = 归入的张数（**且 > 0**）
- 删组前列表里有卡 → 删后卡变少、组消失
- **回收站里那条记录的类别 = "闪卡"**（按 `.trash-item__kind` 精确匹配，不是正文里随便有「闪卡」二字）
- 文件夹改名后**组头标题**跟着变（不是只有 chip 变）

## 8.3 这轮最值得记住的：三条 0=0 的假绿

第一次跑新 CDP 脚本 **27/28 通过**，看起来很好。但三条 ★ 关系断言的实参是这样的：

```
★ 点组头勾整组：已选数 = 该组卡数 :: sel=0 groupSize=0
★ 多选模式下导出按钮张数 = 已选张数 :: export=0 sel=0
★ 归入后该文件夹组头计数 = 归入的张数 :: assignedN=0 sel=0
```

**0 等于 0，断言成立，但一条都没验到。**

根因：脚本用 `document.querySelector(".fcx__ghead")` 取**第一个**组头。
而按文件夹分组时排最前的是刚建的**空文件夹**（计数 0）—— 于是"勾整组"勾了个空组、
"导出已选"导出 0 张、"归入"归了 0 张。

修法不是改断言的字面，是让**两边都非零**：
- 勾组头改成按标题锁定「未归入文件夹」那一组（那组一定有卡）
- 新增一条 `★ 挑中的组非空`（`groupSize > 0`），它先失败，后面三条才有意义
- 导出/归入断言都加 `> 0` 前置

> **规律**：凡"A = B"形式的断言，都要问一句"会不会两边都是 0 / 都是空"。
> 加一条同域的前置断言（"这里本来应该有东西"）比多加十条等式断言更有效。

### 还在截图里抓出第四个盲区：回收站"装没装下全部"

CDP 全绿之后我按硬约束 1 去**看截图**（`10-trash.png`），发现那条记录写的是
「还原时一并恢复 **10** 条关联内容」，而我们删的是 **11** 张。第一反应是"少算了一张"。

查源码（`src/core/trash.ts:145`）确认**不是 bug**：

```ts
attachments: entries.slice(1).map(...)   // 主记录不算在 attachments 里
```

1 主 + 10 关联 = 11，正确。

**但这暴露了真盲区**：原来的断言只验"回收站里有没有一条 kind=闪卡 的记录"。
如果 `removeMany` 只把**第一张**塞进回收站、其余 10 张直接删掉，那条断言照样全绿 ——
用户看到的是"回收站里有一条闪卡记录"，实际上另外 10 张已经永久没了。

补第 38 条断言（数量关系，不是存在性）：

```
★ 回收站那条记录装下了全部被删的卡（1 主 + N 关联 = 删掉的张数）
  :: trash={"attachments":10,"total":11,"text":"还原时一并恢复 10 条关联内容（10 条闪卡）"} deleted=11
```

反向验证（`moveToTrash(entries.slice(0, 1))`，只塞第一张）→ **RED**
`trash={"attachments":0,"total":1}` vs `deleted=11`，37/38。

> 这条经验值得单独记：**"有记录"和"记录完整"是两件事**。
> 凡是"批量操作写一条汇总记录"的地方（回收站、导出、备份），
> 都要验"记录里的条数 = 操作的条数"，而不是"记录存在"。

> 另外，这条是**看截图**发现的，不是断言发现的 —— 硬约束 1 说"断言全绿不算交付"，
> 这次就是这个规律的实例：38 条断言全绿，但截图里一个数字对不上。

```markdown

> **题目**
> 求 $e^{(1+j2\pi)t}$ 的实部。

> 1. 欧拉公式展开
> ⚠️限制条件：$t \ge 0$
> ❌坑：漏掉 $\cos$ 的周期因子
```

**嵌套式**（`高数/数列极限错题闪卡.md`）：

```markdown
> [!question] 2.2
> **题目**：下列极限存在的是
> (A) …
>
> > [!answer] ✅答案：A
> > 知识点：夹逼准则

```

**关键实现细节（三条都是踩过坑才对的）**：

1. `readBlock(lines, start)` 从 **`start + 1`** 开始收行 —— 头部那行的标题已单独解析，再收进正文会让正面变成 `导数定义\n[!tip] 闪卡 7｜导数定义`（首跑 8 条红的根因）。

3. 标签行 `#flashcards/xxx` 只设 `sectionTags`，**不吸进卡片正文**（Spaced Repetition 插件会把标签行吸进正面，是它的缺陷，导入侧要避开）。

**导入面板** `src/v2/ui/FlashcardImportPanel.tsx`：选文件 → 解析 → 报告（认出 N 张 / 其中 M 张库里已有 / 文件里的卡组 / 另有 K 行不是卡）→ 预览前 5 张 → 选归属和标签 → 导入。
